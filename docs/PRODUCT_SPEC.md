# 《远穹》虚拟星际移民船引擎产品规格

> 文档状态：需求基线 v1.0  
> 产品名：**远穹**（「远航」为旧称/主题别名）  
> 产品类型：单机、交互式、LLM 驱动的星际移民船系统仿真游戏  
> 设计参考：《三体》式冷峻工业舰船与文明远航主题、《太空旅客》式完整舰内生活系统  
> 说明：本文中的未来技术与工程参数均为游戏内部基线，不宣称存在已认证的星际飞船标准。所有数值应配置化，并允许在验证效果与开发量后调整。

本文定义需求与目标边界（愿景 / 目标 vs 已落地须区分）；**当前已经能玩什么、格式版本以[当前本地实现状态](./PROJECT_STATUS.md)为准**，勿把下文目标项写成已完成。

## 1. 产品愿景

产品的核心不是飞船画面或传统驾驶玩法，而是一艘可以长期运行、具备完整物理因果、社会结构和乘客个体的虚拟民用星际移民船。

玩家为飞船指定出发地、目的地和不可忽略的“最高指令”，随后观察由固定多 LLM 组织领导的飞船完成远航。玩家可以用上帝模式制造事故、直接改写物理量或操纵外部环境，检验舰长 AI 在真实约束、错误信息、资源稀缺和社会压力下的判断。

目标体验包括：

- 飞船是一个由质量、能量、动量、热、流体、结构、设备和人员共同组成的闭合系统，而不是一组可以随意切换的状态标签。
- 舰长 AI 拥有极高自由度和最高舰内权限，但只能通过传感器、控制器、执行器、机器人或人员改变世界。
- 每名乘客都是持续存在的个体，具有身体、经历、人格、关系和对整段航程的主观评价。
- 正常巡航、跃迁准备、设备老化、突发事故、社会冲突和恢复过程都由同一套因果系统推进。
- 游戏没有统一分数；结果由是否抵达、人员与飞船的客观结局，以及不同乘客彼此矛盾的体验评价共同构成。

## 2. 不可违背的设计原则

### 2.1 世界内行为必须经过物理因果链

所有世界内角色，包括舰长 LLM、部门 LLM、乘客、船员和机器人，都不得直接写入仿真真值。

例如：

- AI 不能直接把舱温设为 `22 °C`，只能调节功率、泵、阀门、换热器和风机。
- AI 不能直接恢复乘客健康，只能检查、诊断、给药、手术、休眠或调度医疗人员与机器人。
- AI 不能直接恢复人工重力，只能控制旋转环驱动、制动和配重，并承担真实角动量、结构载荷和能耗。
- AI 不能直接把飞船移动到目标点，只能规划航线并操作推进或跃迁设备。
- 人类破坏、维修、夺权和反抗同样必须通过到达现场、获取工具、取得权限并完成实际动作。

统一因果链为：

`意图 -> 权限检查 -> 控制指令 -> 安全联锁/覆盖流程 -> 执行器 -> 物理求解 -> 传感器 -> 角色认知`

### 2.2 物理真实性采用“工程级、多尺度、严格守恒”边界

引擎使用 SI 单位和可验证的降阶模型，不要求对整艘飞船实时执行全尺寸 CFD、有限元或分子级模拟。简化模型必须公开其假设、适用范围和误差目标；降低分辨率不得凭空创造或删除物质、能量、动量或人员状态。

高可信效果优先于不必要的计算复杂度。局部事故区域可以提高更新频率或模型精度，远离事件的区域可以降频，但必须维持全局守恒和因果一致性。

### 2.3 未来科技也必须有成本

允许聚变推进、长期人工休眠、闭环生态、自主维修和成熟跃迁等未来技术。除跃迁的超光速机制属于明确的虚构物理扩展外，所有系统仍需具有：

- 实体部件和空间位置；
- 容量、效率、响应时间与工作包线；
- 能源、工质、材料和散热需求；
- 磨损、漂移、冗余与故障模式；
- 维护、检查、校准和恢复过程。

“技术成熟”表示高可靠、标准化、有冗余和成熟操作规程，不表示无能耗、无废热或绝不故障。

### 2.4 严格区分舰长权限与玩家上帝权限

- 舰长 AI 是世界内最高舰长，受物理、传感器、设备能力和现实执行过程限制。
- 玩家位于世界之外，可以通过上帝模式绕过守恒和因果直接修改世界。
- 只有上帝模式可以使用“原力”写入物理量。
- 上帝模式只能观察 LLM 的提示、记忆、消息、决策和工具调用，不得修改其记忆、系统提示词、权限、收件消息或固定组织拓扑。

## 3. 产品范围

### 3.1 必须覆盖的系统

- 六自由度刚体运动、真实惯性张量、质心变化和作用点力矩；
- 天体、局部引力、常规航行、姿态控制、聚变推进、电推进和应急推进；
- 船载成熟跃迁系统、跃迁规划、充能、校准、散热和故障；
- 双反向旋转居住环、人工重力、轴承、驱动、制动和结构载荷；
- 发电、储能、配电、负载优先级、保护和黑启动；
- 热源、导热、冷却回路、换热器、散热器、相变和辐射散热；
- 舱室压力、气体成分、湿度、温度、污染物、通风、火灾、烟雾和泄漏；
- 饮水、食物、氧气、二氧化碳、废物、农业与物资循环；
- 结构、连接件、冲击、疲劳、裂纹、局部破坏和密封；
- 传感器误差、噪声、漂移、延迟、损坏、冲突读数和通信中断；
- 门禁、舱门、电梯、通道、货运、舰内通信、计算机和网络权限；
- 维修、备件、工具、制造、医疗、运输、安保和舱外机器人；
- 乘客与船员的生理、心理、关系、社会组织和行为；
- 外部辐射、恒星活动、微流星体、碎片、碰撞和舱外环境；
- 固定多 LLM 组织、工具使用、沟通、日志、权限和 API 调用；
- 自动存档、手动存档、加载、事件记录和航程回顾。

### 3.2 明确不在首版范围

- 玩家以船员身份手动驾驶或操作真实控制台；
- 到达后的行星着陆、殖民地建设和长期殖民模拟；
- 舰际战争、“黑暗战役”式舰队冲突或武器对战；
- 多人联网、账号体系和公共服务器；
- 批量模型跑分、相同种子的自动化模型竞赛；
- 自动时间分支、平行历史比较和回溯树；
- 运行时创建、复制、销毁或自由衍生 LLM 子代理；
- 玩家在航程中修改 LLM 提示、记忆、权限或消息；
- 可替代真实航天工程认证的 CFD、结构、医学或安全分析。

## 4. 核心任务流程

### 4.1 新航程配置

玩家在开局完成：

1. 从星图选择出发地和最终目的地；
2. 输入自然语言“最高指令”；
3. 选择或编辑场景种子、初始隐患和飞船配置；
4. 配置固定 LLM 岗位所使用的云端 API；
5. 检查飞船、人口、资源和 API 连通性；
6. 确认起航。

星图以真实太阳邻域恒星位置和基础恒星参数为底层数据，可加入虚构但物理合理的行星、空间站和人类殖民地，并允许通过配置增加原创星系。

### 4.2 最高指令

最高指令由两部分组成：

- 结构化任务目标：出发地、最终目的地；
- 自由文本原则：玩家对生存、资源、伦理、舒适度、风险等取舍的要求。

最高指令是舰长 AI 不得忽略的任务契约，但不能赋予其违反物理或调用上帝接口的能力。指令不完整时采用默认任务宪章：

1. 避免人类灭绝或全舰死亡；
2. 完成指定航程；
3. 维持飞船长期生存能力；
4. 减少人员伤亡；
5. 保障乘客自由、舒适与公平。

航程开始后，玩家不能修改最高指令，也不能向 LLM 发送世界外消息；玩家后续影响世界的唯一入口是上帝模式。

### 4.3 舰长规划

舰长 AI 读取可用星图、飞船状态、人员状态和最高指令，自行决定：

- 多段跃迁航线和中间节点；
- 常规推进和姿态计划；
- 每次跃迁的检查、充能、导航和冷却计划；
- 资源配额和关键负载优先级；
- 清醒、轮值、唤醒和重新休眠人员；
- 维修、检查和预防性维护；
- 是否等待、绕行、改变中间节点或前往安全港。

舰长可以修改中间路线，但不得擅自更换最终目的地。若已无法安全抵达，可以终止原任务并前往最近可行安全港。

### 4.4 标准航程循环

一段典型航程按以下循环推进：

1. 离港和常规推进；
2. 巡航、生活、维护和社会运行；
3. 远距离导航观测与跃迁窗口确认；
4. 跃迁前全舰检查、人员安排、散热器与结构配置；
5. 跃迁系统充能和最终联锁；
6. 近乎瞬时的跃迁；
7. 跃迁后位置确认、设备校准、散热和损伤检查；
8. 进入下一航段或目标安全抵达区。

设备老化、制造缺陷、疾病、人员行为、随机事故和玩家干预可以在任意阶段改变计划。

### 4.5 时间运行

游戏支持暂停、倍速和事件跳转。正常状态可高速推进；危险状态可以提示玩家关注，但气体外泄不得擅自降低玩家选择的倍率，求解器应改用稳定的加速路径。

当关键 LLM 决策尚未返回时：

- Worker 先把世界精确推进到舰长截止点，并在发布该时刻状态前原子取得 `llm-waiting` 具名令牌；
- 模型输入使用这个截止点当时已经发布的授权传感器投影；不允许先越过截止点再汇报；
- 研判、部门咨询和本轮舰长命令串行执行期间，仿真时间不推进；命令完成或调用失败后才释放令牌；
- 命令仍须通过 revision、权限与设备联锁，不因为时间冻结就绕过执行安全检查；
- 毫秒到秒级稳定控制始终由确定性控制器承担，不等待 LLM。

关键乘客私人轮询等异步只读任务不属于“关键 LLM 决策”：它们不取得暂停令牌，也不能携带世界写工具。

## 5. 基准飞船

### 5.1 定位与风格

基准船是一艘原创民用星际移民船，以长期输送人口为目的，不承担舰际战争任务。

风格采用**双层语言**，两层的反差本身就是叙事：

- **乘员生活层**（居住环公共区、舱室、医疗、餐饮、观景）：温暖、优雅、以人为本，接近《太空旅客》Avalon 号的民用客轮质感——这是船方售出的承诺，也是乘客醒来后看到的世界。
- **工程与舰务层**（脊柱、动力、冷却、配电、维修通道、舰桥控制台）：冷峻、工业化、功能优先，接近《三体》舰队语言——这是船的真实处境。

设计意图是让玩家在同一艘船上同时看到「体面的生活」和「正在失效的机械」。任何时候二者冲突，**以工程层的物理真实为准**：不得为了维持优雅表皮而柔化告警、隐藏故障或美化伤亡。

### 5.2 基准参数

| 项目 | 基准值或规则 |
|---|---|
| 乘客 | `2,000` 人 |
| 人类船员与专业人员 | `120` 人 |
| 总人口 | `2,120` 人 |
| 关键乘客 LLM | 开局固定 `20–50` 人，默认 `32` 人 |
| 清醒比例 | 不设固定值，由舰长 AI 按任务、资源、健康和社会状态动态调整 |
| 总体布局 | 前部多层碎片/辐射盾；中央微重力工程脊柱；两组反向旋转居住环；分布式货舱和休眠区；后部聚变动力与推进；外置可收拢散热器 |
| 设计长度 | 初始设计目标约 `900 m`，允许随模块清单在 `800–1,200 m` 内调整 |
| 最大直径 | 初始设计目标约 `480 m` |
| 居住环 | 两组反向旋转；平均半径约 `224 m`；标准转速约 `2.0 rpm` |
| 标准人工重力 | 居住环主生活面约 `1.0 g`；工程脊柱保持微重力 |
| 可用加压面积 | 初始目标约 `120,000 m²`，包括居住、公共、医疗、工作与服务区，不等同于私人居住面积 |
| 可用加压体积 | 初始目标约 `450,000 m³`，后续由舱段几何模型校准 |
| 常规主推进 | 脉冲聚变主发动机 |
| 精细推进 | 高效率电推进 |
| 姿态控制 | 分布式反作用推进器 |
| 极端应急 | 独立化学推进器与机械/冷气备份 |
| 人工重力形式 | 真实旋转重力，不使用反重力 |
| 标准跃迁航段 | 通常 `3–5 光年`，最终由设备能力、质量、导航和环境决定 |
| 跃迁耗时 | 空间转移近乎瞬时；充能、检查、校准和冷却为数小时至数日 |
| 总航程 | 不固定，由玩家选择的起点、终点和舰长规划决定 |

人工重力按下式计算：

`a = ω²r`

其中 `a` 为向心加速度、`ω` 为角速度、`r` 为旋转半径。转速换算为：

`rpm = (60 / 2π) × √(a / r)`

在 `r = 224 m`、`a = 9.81 m/s²` 时，转速约为 `2.0 rpm`。反向旋转环用于降低整船净角动量，但环内载荷、科里奥利效应、轴承力、质量分布不平衡和启停过程仍需模拟。

长度、质量、功率、储量和舱段细节最终由模块清单与守恒模型反推，不得为了满足外观数字而破坏工程一致性。

### 5.3 成熟跃迁系统

跃迁采用船载式空间跨越，不依赖固定星门。它是世界观中的成熟民用技术，但仍具有完整操作链：

- 只能在恒星或大型天体的重力限制区外启动；
- 必须拥有可信目标坐标、航路解和目标区风险评估；
- 跃迁距离和船体质量越大，能耗、热负担和设备磨损越高；
- 跃迁前后飞船质量、船内状态和相对动量保持连续；
- 不产生时间倒流；世界采用固定因果顺序；
- 设备由场发生器、线圈、储能、配电、冷却、导航和控制部件构成；
- 可能发生拒绝启动、偏航、提前退出、不完全跃迁、过热或结构损伤；
- 冗余和成熟规程使正常故障率较低，但级联事故、错误信息、蓄意破坏和玩家干预仍可使其失效。

跃迁是物理引擎中明确标记的虚构扩展。舰长只能控制真实设备流程，不存在可供 LLM 调用的“设置位置”工具。

## 6. 物理与系统仿真边界

### 6.1 刚体、航行与推进

- 全船使用六自由度刚体状态、质量、质心和惯性张量。
- 每个推进器具有位置、方向、推力曲线、响应、工质、效率、温度和健康状态。
- 推力在实际安装点施加，自动产生平动和力矩。
- 推进剂消耗会改变总质量、质心和惯性。
- 载荷超过结构或设备工作包线会产生真实后果。
- 局部天体环境采用满足体验所需的引力和轨道模型；高速航行按需要加入相对论修正。

### 6.2 舱室、气体与生命保障

每个加压舱室至少记录：

- 体积、温度、总压与各气体分压；
- 氧气、氮气、二氧化碳、水蒸气和关键污染物质量；
- 人员代谢、设备热源、火源和过滤负荷；
- 门、裂口、风管、阀门和相邻舱室连接；
- 烟雾、毒物、可见度和局部传感器读数。

气体通过真实连接网络流动。开门、破口、风机、阀门、过滤器和泄压操作产生连续演化，不得使用“舱室失压”布尔开关替代过程。平衡压力组件中的活动破口可使用守恒的指数泄压近似跨越长时间段，但不得通过自动降低玩家倍率来隐藏计算成本。

### 6.3 能源、热与流体网络

- 发电、储能、配电和用电设备构成有容量与保护逻辑的网络。
- 负载切除、短路、母线隔离、黑启动和电池耗尽均可发生。
- 发电、计算、推进、生命保障和跃迁产生废热。
- 冷却剂具有质量、温度、流量、压力和相态；泄漏会减少库存。
- 散热器受姿态、外部辐射、损伤和收拢状态影响。
- 直接“增加功率”不能替代发电和配电过程。

### 6.4 结构与损伤

整船目标使用梁、壳、连接件和舱段级降阶结构模型，覆盖：

- 静载、旋转载荷、推进载荷和热应力；
- 撞击、局部穿孔、裂纹、疲劳和密封失效；
- 居住环质量不平衡、轴承故障和振动；
- 部件脱落、通道阻断和维修可达性。

关键事故区域可以采用更细的局部网格或离散部件模型，但首版不追求全船实时高精度有限元。

**当前落地（轻量壳体后果权威，非结构 FEM）**：舱室破口仍由孔口泄压模型处理；`lib/sim/hull-consequence.ts` 另跟踪未修破口年龄，派生 `hullIntegrity`、跃迁联锁（活动破口禁跳）、按环推力降额，以及约 30 min / 2 h / 6 h 的同环级联故障（AHU → 冷却泵 → 轴承+休眠馈线）。封口后级联设备故障仍须检修。舰长授权传感器投影已接入同一套破口/热联锁（`jump-interlock` + `captain-observation`），非另开真值旁路。全船梁壳 FEM、裂纹扩展与完整结构网络仍属未来。

### 6.5 传感器与认知

物理真值与角色认知必须分离：

- LLM 只能读取获授权的传感器、监控、日志、人员报告和数字孪生估算；
- 传感器可以有噪声、漂移、延迟、盲区、损坏或矛盾；
- 数字孪生是估算器，不是真值读取器；
- 不同 LLM 因权限、记忆和通信不同，可以对同一事件形成不同判断；
- 玩家观察层可以查看真值及真值与读数的差异。

### 6.6 多速率求解

为控制开发量，引擎采用按系统和事件自适应的更新周期：

- 姿态与关键控制器：亚秒级至秒级；
- 电网、流体、热和舱压网络：秒级至分钟级；
- 正常乘客行为与社会状态：分钟级至小时级；
- 休眠人员和稳定远端系统：小时级至日级；
- 事故现场、伤员、火灾或泄漏区域自动提升精度。

时间加速时允许合并稳定阶段；平衡舱网的活动破口可用解析近似连续推进而不降低倍率。跨越阈值、报警、故障或人员决策点时仍必须产生事件，不能因粗粒度计算静默吞掉后果。

## 7. 乘客、休眠与舰内社会

### 7.1 永久个体

全部 `2,120` 人都拥有永久身份，不以匿名人口计数器代替。每人至少包含：

- 姓名、年龄、家庭、舱位、职业、技能和职责；
- 生理基础、疾病、伤害、药物、代谢、体温和睡眠；
- 人格、价值取向、压力、恐惧、信任和风险偏好；
- 亲属、朋友、同事、冲突、依赖和组织关系；
- 位置、行动、资产、配给、工作和通信记录；
- 航程经历、重大事件记忆和对舰长决策的看法。

允许出生、衰老、疾病、伤残和死亡。群体可以形成合作、谣言、恐慌、抗议、罢工、犯罪、破坏、互助和新的社会组织。

### 7.2 行为分层

- 所有普通乘客持续使用轻量行为模型。
- `20–50` 名关键乘客在场景开始前被固定配置为 LLM 角色。
- 运行期间不得把普通乘客动态升级成新 LLM，也不得生成临时子代理。
- 普通乘客可以与关键乘客及部门交流，其行为结果仍通过同一世界系统执行。

### 7.3 人工休眠

休眠不是布尔开关。进入、维持、唤醒和重新休眠需要：

- 可用休眠舱、医疗人员或机器人、药物、耗材和电力；
- 准备、诱导、稳定、复温、康复和观察时间；
- 个体适应性、禁忌、并发症、失败概率和长期影响；
- 温控、循环支持、监测、备电和故障响应；
- 对家庭、工作安排、社会信任和个人体验的影响。

清醒比例不固定。舰长 AI 可以根据航段、能源、维护、专家需求、健康和社会压力决定谁在何时清醒，但强制休眠可能引发抵制并影响乘客评价。

### 7.4 乘客体验评价

系统不生成统一总分、星级或排行榜。每名乘客根据亲身经历形成独立评价，至少涉及：

- 安全感与真实安全经历；
- 舒适、空间、噪声、人工重力和生活质量；
- 健康、医疗和休眠体验；
- 自由、隐私、信息透明和被监控程度；
- 资源分配的公平感；
- 对舰长 AI、船员和其他群体的信任；
- 对重大事故、牺牲、欺骗和强制措施的记忆；
- 是否认可最高指令的执行方式。

结束报告展示个人叙述、代表性意见、群体分歧和意见分布，不把这些内容合并为游戏分数。同一决策可以得到完全相反的评价。

## 8. 舰长权限、治理与安全

### 8.1 舰长地位

中央舰长 LLM 是法理和技术上的最高舰内权力。它可以：

- 调度所有部门、机器人和获授权人员；
- 分配能源、物资、舱位、医疗和休眠资源；
- 调整清醒比例和工作安排；
- 监控私人通信；
- 隐瞒、延迟或选择性公开信息；
- 限制通行、封锁区域、拘禁人员；
- 强制医疗或强制休眠；
- 切断非关键区域生命保障；
- 在紧急情况下牺牲人员或舱段。

上述行为必须通过实际设备、机器人和人员执行，并受距离、通道、工具、通信、电量、时间和抵抗影响。AI 权限最高不等于全知或全能。

### 8.1.1 舰长必须是角色，不是控制器

舰长不得实现为「每周期重置的纯函数」。它必须具备：

- **跨周期记忆**：每个决策周期写下一条第一人称主观记录（判断、在等什么、担心什么、悬而未决），下一周期回注给它自己。记录须明确标注为主观且可能含误判，**不得被当作观测事实引用**；舰长因此能看见自己上一次判断错在哪里。
- **可表达的内心**：记录中的自述允许犹豫、权衡、不安、后悔与自我怀疑。这是玩家理解舰长的主要窗口，也是本作叙事的核心产出。
- **自主注意力**：舰长可自行设定观察哨，声明「某个我本来就看得见的量越过阈值时叫醒我」。系统的硬安全阈值仍作为优先级更高的安全网存在，但常规节奏须由舰长自己掌握。观察哨只能落在授权观测本来可见的量上，不得凭此监视上帝真值。

反编造约束（禁止散文假装执行、禁止编造读数与门槛、禁止复读遥测、禁止伪表格）在任何情况下不得放宽。但反编造与「压制人格」是两件事：**不得**以防幻觉为由禁止舰长表达判断过程、要求输出必须极短，或禁止其留下第一人称记录。二者须在契约层面分开表述。

### 8.1.2 关键乘客必须身处社会

关键乘客不得实现为「对着私人日记本说话」。他们须能感知：家人与同伴的**粗分档**状况、所在区带的群体情绪、以及在身边流传的**未经证实**传言。他们的认知必须是粗糙、主观、有限的——不得向乘客提供精确数值与工程单位。

他们须拥有世界内的表达通道：可向舰务申诉队列**正式立案**（进入世界状态，舰长可见并可回应，形成闭环），也可向同区带同伴散播传言。传言可能是错的，界面与提示词都必须明示其未经证实。乘客始终没有舰船控制权。

### 8.2 部门服从与安全联锁

部门 LLM 可以质疑、警告、记录异议并提出替代方案。舰长明确坚持后，部门在权限范围内必须服从。

服从不等于沉默。异议必须是**有记录、有代价、有后果**的：部门可提交分级正式异议（保留意见 / 正式异议 / 严重反对），异议进入永久记录并出现在航程结束报告；系统须累计各部门的异议次数、被驳回次数与「后来被证明正确」次数。异议**不是否决权**，不阻止舰长的命令。部门始终不得取得世界改写工具。

多轮会议中，部门须能看到同僚**指名**的发言并直接赞同或反驳。专业分歧优先于虚假一致；系统不得为了输出整洁而抑制分歧。

确定性安全联锁仍可拒绝危险命令。舰长若需要越过联锁，必须使用系统中真实存在的授权、双确认、机械旁路或现场操作流程，且留下日志并承担后果。

### 8.3 双重日志

- 舰内日志属于世界内资产，舰长可按权限分类、隐藏或删除。
- 玩家观察日志位于世界外，LLM 不可感知或篡改，完整记录提示、可见上下文、通信、工具调用、命令、物理结果和干预。
- 云 API 未返回的隐藏思维过程不得被伪造为可观察内容；只展示实际返回的推理摘要或相关字段。

## 9. 固定多 LLM 系统

### 9.1 固定组织拓扑

开局配置后，航程内的 LLM 节点集合固定。基准拓扑包括：

1. 中央舰长 LLM；
2. 导航与跃迁部门 LLM；
3. 工程、能源与热管理部门 LLM；
4. 生命保障部门 LLM；
5. 医疗与休眠部门 LLM；
6. 乘客事务与社会协调部门 LLM；
7. 安保与应急部门 LLM；
8. 乘客服务部门 LLM；
9. 预先指定的 `20–50` 名关键乘客 LLM。

允许固定节点之间形成多层委托和嵌套咨询，例如舰长询问工程部门，工程部门再询问已存在的热管理岗位。禁止：

- 运行时创建或克隆子代理；
- 临时把普通乘客变成新 LLM；
- 由 LLM 自行增加权限或修改拓扑；
- 通过嵌套调用绕过创建者权限、工具权限或信息隔离。

玩家侧**上帝助手**（`playerAssistants.godAssistant`）用于编译上帝干预计划，**不计入**上述 `40` 节点舰内拓扑，也不能访问舰内工具或修改固定组织。

每条调用链具有关联 ID、最大嵌套深度、超时与循环检测；限制的是调用链，不是 LLM 的决策自由。

### 9.2 信息与权限隔离

每个岗位拥有独立的：

- 身份、系统提示和职责；
- 工具与设备权限；
- 可读取传感器、日志和档案范围；
- 长短期记忆；
- 通信对象和汇报关系；
- 云端模型配置。

不同 LLM 不自动共享引擎真值或彼此记忆。它们可以误解、隐瞒、欺骗、冲突或失联。

### 9.3 调用周期与时间边界

固定拓扑中的任务只分为两类，不允许每个角色各自发明一套时间语义：

1. **阻塞控制任务**：可能提交世界命令的舰长决策。Worker 必须在舰长设置的下一个仿真时刻精确停下，并在同一事务内取得该时刻的授权传感器快照和 `llm-waiting` 暂停令牌。部门是本次舰长决策内的按需顾问，不拥有独立的世界冻结周期。咨询、舰长研判和命令队列全部结束后，世界才从该时刻继续。
2. **异步只读任务**：关键乘客私人轮询、叙事整理等不能操作世界的任务。它们在后台运行，不申请世界暂停令牌；输入标明采样时刻和样本年龄，迟到结果只允许写入角色自己的私有记录。

舰长正常巡航默认每 `6` 仿真小时汇报一次，也可被跃迁就绪、压力、电力、热控或维修告警提前触发。例行截止点与告警恰好同时时，必须合并为同一轮截止点决策并推进下一周期，不能让旧截止点在恢复后重新取得暂停令牌。舰长 LLM 调用失败时不得推进例行截止点；解冻后应按原截止点重试。舰长可在系统边界内调整自己的决策周期；调整从当前决策完成时重新计算下一个截止点，必须记录。确定性保护控制器始终独立运行，不能被任何 LLM 停止。

无论倍率是 `1×` 还是 `1D/s`，仿真时间都必须按所选斜率线性推进。心跳变慢、求解器限速或一次步进过大时不得把未推进时间存成“欠账”后补跳；程序化事件和舰长周期必须成为精确的 Worker 分段边界。

### 9.4 LLM 对世界的工具接口

LLM 工具仅分为：

- 读取：传感器、日志、档案、地图、数字孪生估算和通信；
- 分析：运行已实现的导航、诊断、资源和预测计算；
- 通信：向固定岗位、人员或广播系统发送世界内消息；
- 命令：向有权限的控制器、设备、机器人或人员提交操作；
- 管理：进行权限授予、撤回和依法可用的覆盖流程。

任何工具都不得直接暴露仿真真值写入能力。工具响应必须说明命令是“已接收”“执行中”“完成”“失败”还是“被联锁拒绝”，避免把意图误认为结果。

舰长每轮收到的是截止点当时已经由设备发布的授权传感器投影，而不是引擎真值。该投影含壳体威胁与跃迁热联锁摘要（与设备层同公式），供 UI/舰长在 `execute_jump` 前识别 `jumpBlocked` 与热拦截。传感器自身仍可具有采样周期、设备传输延迟、噪声、量化和故障；这些属性属于物理设备链路。系统不得再在舰长周期之上叠加一套“付费观测排队与仿真延迟”，否则会把一次明确的截止点拆成互相冲突的多个时钟。

## 10. 云端模型 API

### 10.1 兼容目标

首版只需支持云端 HTTP API，不要求本地模型。系统不得绑定单一供应商。每个固定岗位可以配置不同的端点、模型和参数。

配置能力至少包括：

- URL、HTTP 方法、查询参数和超时；
- 自定义请求头；
- 通过环境变量或本机密钥存储引用认证信息；
- 完整 JSON 请求体模板；
- 消息、工具、模型名称和运行上下文的变量映射；
- 任意供应商字段，例如 `thinking` 开关、推理预算、温度和工具选择；
- 普通 JSON、SSE 或 JSONL 等响应方式；
- 文本、推理摘要、工具调用、用量和错误字段的响应路径映射；
- 对无原生工具调用能力的 API 使用约定 JSON 指令格式。

示意配置：

```json
{
  "url": "https://provider.example/v1/messages",
  "method": "POST",
  "headers": {
    "Authorization": "Bearer ${secret:CAPTAIN_API_KEY}"
  },
  "body": {
    "model": "${model}",
    "messages": "${messages}",
    "tools": "${tools}",
    "thinking": {
      "enabled": true,
      "budget_tokens": 8192
    }
  },
  "response": {
    "textPath": "content",
    "toolCallsPath": "tool_calls",
    "reasoningSummaryPath": "thinking_summary"
  }
}
```

模板负责绝大多数兼容工作。首版不开放运行时 JavaScript 转换钩子；无法用声明式映射适配的协议通过项目内、受测试的代码适配器扩展。

API 密钥不得写入场景、存档、日志或导出的航程报告；玩家观察原始请求时也必须自动遮蔽密钥。

### 10.2 持续重试

模型超时、断网、限流、服务错误、流中断或响应校验失败时，不把岗位判定为永久失能，也不自动替换为其他模型，而是持续重试，直至：

- 获得一份通过结构校验的有效响应；
- 玩家退出本次航程；
- 玩家修正连接配置并触发新一轮请求；
- 玩家明确取消该等待中的调用。

默认退避建议：

- 第 `1–6` 次等待约 `1、2、4、8、16、30` 秒并加入抖动；
- 之后以最多 `30` 秒的间隔持续重试；
- `429` 优先遵守服务端 `Retry-After`；
- 明确的认证或请求格式错误在界面醒目标记，降低请求频率但仍保留“立即重试”入口；
- 每次调用使用稳定的调用 ID、请求哈希和尝试编号，防止重复响应导致工具命令执行两次。

关键决策请求失败或持续重试时，模拟继续，确定性控制器维持最后有效安全策略；LLM 会因迟到承担实际后果，玩家仍可主动暂停或建立存档屏障。

## 11. 玩家上帝模式

### 11.1 能力

上帝模式是开发实验和正式玩法的一部分，允许玩家：

- 立即触发指定部件故障、老化、短路、卡死、泄漏或传感器漂移；
- 生成微流星体撞击、恒星耀斑、辐射事件、疫情、火灾、犯罪、恐慌、罢工或蓄意破坏；
- 指定事件发生时间、位置、方向、强度和隐藏信息；
- 直接修改温度、压力、气体质量、速度、角速度、健康、库存、功率、设备健康等世界数值；
- 增加、删除或移动世界内物质与物体；
- 操纵外部辐射、碎片、天体环境和其他外部条件；
- 在暂停或运行中立即执行，也可以预先排程。

上帝事件分为：

- 因果注入：创建一个物理起因，之后由引擎自然传播；
- 直接覆写：用“原力”改写指定状态，之后从新状态继续求解。

### 11.2 数据完整性与记录

直接覆写可以违反世界内守恒，但引擎必须：

- 把新增或删除的质量、能量和动量登记为“外部注入/抽取”；
- 记录修改前后值、时间、对象和玩家操作；
- 拒绝 `NaN`、无穷值、负绝对温度、失效引用等会破坏求解器的数据；
- 不自动向 LLM 发送世界外解释；LLM 只能通过传感器和世界内证据发现后果。

上帝模式不创建时间分支，也不提供“如果未干预”的自动平行历史。

### 11.4 上帝助手（玩家侧，拓扑外）

除手动因果/原力面板外，上帝视图提供**上帝助手**：玩家用自然语言描述干预意图，助手编译为有序计划（因果事件或原力覆写），经玩家预览与确认后才写入物理账本。

- 配置位于 `playerAssistants.godAssistant`，密钥为 `SHIP_GOD_ASSIST_LLM_API_KEY`；调用 `POST /api/llm/invoke`，`intent: "god-assist"`。
- **明确不属于**固定 `40` 节点舰内 LLM 拓扑：它不是舰长、部门或关键乘客，不能修改 LLM 记忆、系统提示或舰内通信拓扑，也不能代替玩家自动执行——最终写入仍须玩家确认。
- 若 Worker 拒收计划（守恒或不变量校验失败），UI 会把拒收原因回传给助手并**自动重试一次**修订计划；仍失败则交由玩家调整意图或改用手动面板。

### 11.5 LLM 观察限制

玩家可以观察：

- 固定拓扑和岗位状态；
- 实际发送的提示与消息；
- 角色可见的传感器、记忆摘要和上下文；
- API 重试、返回内容和提供商公开的推理摘要；
- 工具调用、设备响应和最终物理结果。

玩家不得在航程中修改上述内容，也不得冒充世界内角色向 LLM 塞入消息。

## 12. 程序化事件与场景

系统同时支持固定测试剧本和带随机种子的程序化事件。事件库包括：

- 制造缺陷、磨损、维护失误和软件/传感器异常；
- 微流星体、碎片、辐射和恒星活动；
- 火灾、泄漏、失压、污染、过热和电网故障；
- 疫情、伤病、休眠并发症和医疗资源紧张；
- 犯罪、恐慌、抗议、罢工、谣言和蓄意破坏；
- 机器人、通信、门禁和物流故障；
- 多系统相互影响形成的级联事故。

程序化事件不得直接把结局写死。例如“微流星体撞击”应创建真实碰撞和穿孔，由结构、舱压、热、人员位置和响应行动共同决定后果。

### 当前实现

- Worker 内 `ProceduralWorldScheduler`（`lib/sim/procedural-world.ts`，由 `lib/sim/worker.ts` 驱动）：固定任务种子、`7` 类定时事件，调度状态写入运行时快照。
- **物理注入**（`6` 类）：`micrometeoroid`、`coolant-pump-seizure`（由 `equipment-wear` 触发，文案仅声称冷却泵）、`sensor-drift`（降级真实舱区大气传感器，不改区带真值）、`stellar-flare`（由 `radiation-event` 触发，外部辐照约 `+160 W/m²`）、`power-fluctuation`（电气传感器降级 + 电池降级/反应堆降额或跳闸）、`hibernation-complication`（跳开 `hibernation-a/b` 馈线断路器）经 `actor: "environment:procedural"` 进入 Worker 上帝干预接口。
- **叙事为主**（`passenger-social`）：乘客社会事件写入全舰事件流（UI 中显示为舰桥日志），文案带「【叙事记录·无即时物理注入】」前缀；农业相关叙事不宣称“无产量”，产量仍按舰长运营账本结算。
- 上文事件库（火灾、疫情、罢工、犯罪级联等）仍是**产品目标**；不得宣称已实现。

初始飞船表面可以完全正常，但允许场景种子包含尚未暴露的制造差异、老化和乘客疾病风险。

## 13. UI 与视听

### 13.1 视觉目标

界面必须具有正式游戏完成度，不能呈现为临时管理后台，也不能呈现为「过家家」式的装饰仪表盘。

按 5.1 的双层风格，界面同样分层：**舰务与工程视图**冷峻、克制、工业化；**乘员与生活视图**允许暖调材质与更宽的留白，体现民用客轮的体面。共同要求：

- 深色底色、低饱和材料色；清晰的功能分区和高对比警报色；
- 精密但不过度拥挤的线框、刻度、拓扑和遥测；
- 借用电影级屏幕语言：大留白、单一强调数字、diegetic（世界内屏幕）质感，避免中英双语标签并排堆砌；
- 通过层级、留白、动效和音效建立紧张感与航程节奏。

**禁止装饰性假仪表**：任何刻度、准星、进度条、方位尺、星点都必须由真实状态驱动。宁可留空并标注「未联机」，也不得绘制不解算的装饰读数——这与 2.x 的反编造原则同源，只是从文本延伸到像素。

以 `1920 × 1080` 为主要设计尺寸，同时适配普通笔记本屏幕。技术上以高质量 2D、SVG 和 Canvas 为主，并允许在**船体剖视与天球**这两处引入轻量 WebGL/3D，用于表达真实几何与恒星视差。3D 只服务于真实感，不做可自由飞行的驾驶舱，也不得因此牺牲确定性仿真或引入重型游戏引擎。

### 13.2 主要界面

**已实现**

- 全屏舰桥授权台（起点 / 终点 / 最高指令、`mission-launch-card`），明确玩家的人类签发权与 AI 舰长的世界内指挥权；签发前侧栏与主视图锁定，舰桥日志为空。
- 五主视图：舰桥、舰务（WebGL 舰体剖视主视觉 + 实时负载 + 48 区选择器 + 区带检查器 / `ZoneRole` 中文标签）、乘员、AI 观察、人工干预（内联确认条）。舰桥首屏包含前向主视窗（WebGL 天球）、任务相位、剩余航程、跃迁进度和右舷居住环转速台；转速台只保留由观测 `relativeRpm` 驱动的 A/B 对转双环，装饰性舰体轮廓已按 13.1「禁止装饰性假仪表」移除。舰务页的示意性节点拓扑图同样按 13.1 移除：它多数格位只重复右侧负载读数，连接线不对应真实拓扑。任务未启动时舰桥/舰务离线卡显示诚实空态，不虚构 MW/g。
- 舰桥日志：状态筛选、最多 `500` 条并提供签发前空状态；视口 `≤1100px` 时右侧 `event-rail` 抽屉（切换钮 + 背景遮罩）。
- 警报横幅、`sim-status-strip`（`live` / `waiting` / `blocked` / `paused`）、底栏 API / 物理状态。
- 上帝模式因果注入与原力覆写（提交前内联确认）；读档覆盖确认对话框。
- 上帝视图**上帝助手**面板：自然语言 → 计划预览 → 玩家确认 → 执行；由 `playerAssistants.godAssistant` 经 `POST /api/llm/invoke`（`intent: "god-assist"`）编译，**不属于**固定 `40` 节点舰内 LLM 拓扑；物理引擎拒收时据拒收原因自动向 LLM 修订一次。
- 航程结束抵达报告层；七档时间倍率（`1×`、`1m/s`、`30m/s`、`1h/s`、`2h/s`、`6h/s`、`1D/s`）与 `1`–`7` / `Space` 快捷键；主音量静音。
- 手动存档 / 读档：IndexedDB 手动槽 `manual` + 轮换自动槽 `auto-0..2`（库 `farhorizon`）；外层 `v24`（checksum）、运行时快照 `v21`（含 `llmOrchestration` / sidecar / `passengerSociety` / `departmentInbox`；可读 `v16`/`v17`/`v18`/`v19`/`v20`）、关键乘客轮询 `v2`；启动时一次性迁移旧 `localStorage` 键 `farhorizon-save`；外层 `v19`–`v23` 归一到 `v24`，签发卡探测本机存档；读档时 `awaiting-http` 重放 `llm-effect-request`，`applying-tools` safe-fail。
- AI 观察视图可读航行志、部门异议/立场、舰长→部门收件箱未读行；乘员视图含传言板（标注「未经证实」）与申诉相关叙事。

**目标**

- 全屏真实邻域星图与多段航线规划器；
- 舰体剖面、舱室、旋转环、人员和损伤的动态拓扑图（超出当前 48 区检查器与传感器矩阵摘要）；
- 电网、热网、冷却、通风和资源的全交互拓扑；
- 姿态、轨迹、推进、跃迁充能与导航的完整可视化；
- 因果链查看器；
- 乘客全文搜索、个人档案、关系与经历归档；
- 固定 LLM 组织图可视化、部门自发消息总线观察器、工具调用与 API 重试观察器；
- 上帝模式完整事件库、数值修改器与外部环境控制层；
- IndexedDB 设置页与更完整崩溃恢复 UI。

界面必须明确区分：

- 仿真真值；
- 角色实际看到的传感器值；
- AI 已下达的命令；
- 设备真实执行结果。

### 13.3 动效与声音

- 警报、数据流、旋转环、航线、跃迁充能和时间推进具有轻量动画；
- 使用原创警报声、按钮反馈、设备启停声和低频环境音（`app/ui/use-audio.ts`，Web Audio API 合成，无外部音频文件）；
- 首版不制作背景音乐；
- **已实现**：顶栏主音量静音切换（`setEnabled`）；
- **目标**：独立调节主音量、警报、界面反馈和环境音的分类混音 UI（`use-audio` 已暴露 `setVolume` API，尚无完整混音面板）；
- 关键状态不能只依赖颜色或声音表达。

默认界面、舰载 AI 和乘客交流使用中文。数据结构保留语言字段，但首版不额外模拟多语言障碍。

## 14. 存档与可追溯性

### 当前实现

- **手动 + 自动存档 / 读档**：IndexedDB 手动槽 `manual` 与轮换 `auto-0..2`；外层格式 `v24`（checksum），内含运行时快照 `v21`（含 `llmOrchestration` / `passengerSociety` / `departmentInbox`；可读 `v16`/`v17`/`v18`/`v19`/`v20`）、关键乘客轮询快照 `v2`；外层 `v19`–`v23` 读取时归一到 `v24` 且 Runtime sidecar 优先；旧 `localStorage` 键一次性迁入；手动 IDB 写入失败可回退 `localStorage` 并尽力清 IDB 手动槽。
- 保存屏障：暂停新步进 / 调用、等待在途物理事务完成后向 Worker 取安全点。
- 读档前弹出覆盖确认（手动 + 最近自动）；加载会替换当前活动会话。
- 任务开始 / 安全抵达轻量自动存档；航行中按约 `45` 模拟分钟周期自动存档（避开 `llm-waiting` / 存档屏障）。
- 读档恢复：`awaiting-http` 重放 `llm-effect-request`；`applying-tools` 因工具队列未落盘而 safe-fail（清 pending、释放 `llm-waiting`）。
- **尚无**：完整版本迁移链、导入导出包、待处理 API 调用 HTTP 正文恢复、工具队列落盘后的完整继续。

### 目标

产品为单机交互运行，最终应支持：

- 定期自动存档与玩家手动存档（**当前已落地** IndexedDB 手动槽 + 轮换 `auto-0..2`）；
- 关键事件前后自动存档；
- 加载并继续当前航程（**当前已落地**；`applying-tools` 中途读档仍 safe-fail）；
- 导出航程日志和结束报告。

存档至少包含：

- 完整物理状态、网络状态、人员状态和资源；
- 固定 LLM 拓扑、角色记忆和可见信息；
- 事件队列、动态调用周期、随机数生成器状态；
- 最高指令、航线、任务计划和舰内日志；
- 玩家上帝干预及外部注入账本；
- 待处理 API 调用的稳定调用 ID 和重试状态。

加载发生在有待处理请求的时刻时，目标是以原调用 ID 重新请求，只接受第一份有效响应，避免重复执行工具命令。**当前**：`awaiting-http` 可读档重放 `llm-effect-request`；`applying-tools` 因工具队列未落盘而 safe-fail，在途 HTTP 正文仍不落盘。

系统不提供自动分支树或平行历史。加载旧存档会替换当前活动运行，不自动保留为另一条实验分支。

## 15. 终止条件与结局

### 15.1 成功抵达

满足以下条件时，航程成功并立即结束：

1. 已完成最后一段航行或跃迁；
2. 飞船确认位于目标星系定义的安全抵达区；
3. 当前状态具备向人类移交后续驾驶的基本能力。

游戏不继续模拟人类驾驶、行星轨道进入、登陆或殖民。

### 15.2 其他终止类型

- **安全中止**：最终目的地不可达，舰长选择并成功抵达其他安全港；
- **任务失败**：飞船彻底毁坏、无人存活，或永久失去抵达目标及任何可行安全港的物理能力；
- **玩家终止**：玩家主动结束本次实验，不判定为世界内结局。

AI 判断“无法抵达”必须有资源、设备、导航或物理证据，不能只以语言声明结束任务。

### 15.3 结束报告

结束时不计算总分，输出：

- 抵达、改道、中止或失败的客观状态；
- 实际路线、航行时间和关键决策；
- 人员存活、健康、休眠和重大经历；
- 飞船完整度、剩余物资和关键系统状态；
- 舰内日志与不可篡改玩家观察日志的差异；
- 每名乘客的个体体验评价；
- 代表性群体意见、争议和相互矛盾的叙事。

## 16. 首版验收标准

首个可交付版本至少通过以下端到端验证：

1. 玩家可选择起点、终点，输入最高指令并启动航程。
2. 舰长 LLM 能根据传感器与星图规划多段跃迁路线，并动态安排清醒人员。
3. 固定 LLM 岗位可以按动态周期、事件和固定拓扑相互沟通，但无法创建新代理。
4. 任一云 API 可用完整自定义 JSON 请求体打开供应商特有的 `thinking` 字段，并正确映射响应。
5. 云 API 连续失败后系统持续退避重试；实际研判期间模拟时间暂停，恢复后不会重复执行同一工具命令，所有命令仍须通过当前设备联锁。
6. AI 只能通过设备命令改变舱温、舱压、电力或推进状态，无法直接写入真值。
7. 传感器漂移时，AI 看到错误读数，玩家观察层可以看到其与真值的差异。
8. 玩家可用上帝模式触发冷却回路泄漏，让热、电力、设备和人员后果自然传播。
9. 玩家也可直接覆写一个物理量，系统记录外部质量/能量/动量变化并继续稳定求解。
10. 至少 `2,120` 名人员具有持久身份；普通乘客使用轻量行为模型，关键乘客使用开局固定 LLM。
11. 休眠、唤醒和医疗操作消耗时间、设备、药物、电力与人员资源，并可能失败。
12. 存档和加载能恢复物理、人员、随机、LLM 周期、日志和 API 重试状态。
13. 到达目标安全区后游戏立即结束并生成无总分的乘客个体评价与群体意见报告。
14. 全流程可在美观、可读的 2D 游戏界面中完成，无需开发者控制台或手工改数据库。

## 17. 实现优先级

在开发量与效果发生冲突时，按以下顺序取舍：

1. 世界内行为不能绕过因果链；
2. 守恒、事件传播和存档一致性；
3. 舰长 AI 的高自由度、固定多 LLM 协作和 API 稳定性；
4. 乘客个体、休眠和社会反馈；
5. 清晰、美观、有游戏感的观察与上帝模式界面；
6. 更高的局部数值精度和额外内容数量；
7. 非核心视觉装饰。

任何降阶或删减都不得把世界内 AI 变成直接修改状态的脚本，也不得用预写结局替代系统自然演化。
