# ship-Y 代码与行为审计

审计日期：2026-09-08。基线提交：`351c42c`。环境：Windows、Node `v26.5.1`。生产业务文件未修改。

**结论：项目存在可以复现的状态一致性、告警、航路和故障恢复问题。大量领域模型与测试已经存在，但用户操作跨越 React、Worker、存档和模型网关之后，缺乏统一的事务与生命周期约束。当前不能把“构建通过”“测试很多”当成产品可靠的证据。**

这也不是一个全部由假数据堆成的空壳。物理域有实际积分、守恒账本、命令权限、快照恢复和回滚实现。本次验证认可这些局部工作；问题在于它们还没有组成行为一致、失败可恢复的完整产品。

## 已复现的问题

### A01 · P1：同类故障只能报警一次，已解除故障仍可能留在活动告警中

位置：[检测器](../../app/ui/components/alert-banner.tsx#L186)、[接收与去重](../../app/mission-control.tsx#L1140)。

复现：冷却温度 `390 K → 300 K → 390 K`，对应首次过热、恢复、再次过热。首次产生 `thermal-critical`，第二次过热产生 **0 条**新警报。

原因：`knownAlertIds` 是整场任务的已见集合，只添加，不随故障解除而删除。`activeAlerts` 只追加和截断，也没有依据当前条件撤销告警。横幅中新增的 dismissed 清理并没有解决上游生命周期问题。

影响：用户确认过一次严重故障后，再发生同类故障可能没有提示或声音；未确认的历史故障又可能继续冒充当前故障。告警系统同时存在漏报与陈旧告警。

修复方向：区分“当前故障实例”“确认状态”“历史事件”；按条件进入、升级、解除、复发更新实例，禁止用设备或规则 ID 充当整局不可重复的事件 ID。

### A02 · P1：读档失败会先替换当前世界的 AI 状态

位置：[开始恢复](../../app/mission-control/use-local-save.ts#L627)、[拒绝处理](../../app/mission-control.tsx#L956)。

复现：使用外层归一化接受、但内部物理快照版本非法的存档。实际 Worker 返回 `unsupported or malformed simulation snapshot`。返回之前，React 已更新航行志等附加状态，`worldEpoch` 从 `1` 变成 `2`。

原因：取消当前决策、更新日程和五类 AI 状态、递增 epoch、清空修订号，全发生在 Worker 确认之前。错误分支只清 pending、释放 token、显示“当前世界保持不变”，没有恢复这些修改。

影响：物理世界是旧的，AI 记忆与日程可能已是另一个存档的。读档失败提示与实际行为不一致。

修复方向：预校验与准备阶段不得修改活动状态；收到指定 restore request 的成功回执后一次提交。失败须保持物理状态、AI 状态、日程、暂停意图及版本标识的一致性。

### A03 · P1：恢复开局配置后，签发按钮永久无响应

位置：[防重复启动锁](../../app/mission-control.tsx#L2206)、[恢复未开局配置](../../app/mission-control/use-local-save.ts#L675)。

触发路径：保留一个未开局的手动配置存档，启动任务，再读回该配置。加载分支将 `missionStarted` 设回 false，开局界面重新出现；但 `missionStartRequestedRef` 仍为 true。

执行实际启动处理函数，结果是 **0 条 initialize 命令、0 条反馈消息**。代码注释认为“启动卡片此后不会再出现”，但读档路径直接推翻了这个前提。初始化失败也没有可见的重新尝试状态。

修复方向：启动锁应属于一次启动事务，而不是组件整个生命周期；明确 idle、initializing、running、failed，并在读档和初始化拒绝时完成状态迁移。

### A04 · P2：空格键劫持按钮操作，模态窗口没有完整的键盘隔离

位置：[全局快捷键](../../app/mission-control.tsx#L1701)、[读档对话框](../../app/ui/components/load-confirm-dialog.tsx#L31)。

复现：事件目标为 `BUTTON` 时按空格，处理器执行 `preventDefault()` 并切换仿真暂停状态。原本应激活焦点按钮的操作被全局处理器接管。

原因：仅排除 input、textarea、select 和 contenteditable；没有排除按钮、交互角色、已处理事件、重复按键或模态打开状态。读档弹窗只声明了 `aria-modal`，没有焦点转移、焦点约束、背景 inert 或 Escape 管理。

影响：键盘操作“确认读取”“取消”等控件时可能改变仿真状态；声明了对话框语义却没有对应行为。屏幕阅读器影响还需要浏览器专项验证。

修复方向：快捷键使用明确作用域，尊重 `defaultPrevented` 与控件默认行为；使用具备完整焦点管理的对话框实现。

### A05 · P1：备用存档写入成功后，恢复 IndexedDB 会读回更旧进度

位置：[读取优先级](../../lib/persist/local-save-idb.ts#L370)、[备用写入](../../lib/persist/local-save-idb.ts#L447)。

复现：IndexedDB 保存 100 秒进度；暂时不可用时，localStorage 成功保存 200 秒进度，删除旧 IDB 槽失败；IDB 恢复后调用实际 `getManualSave`，读回 **100 秒**。

原因：读取无条件优先 IDB；写备用存档依靠“尽力删除旧槽”表达新旧关系。迁移函数发现旧槽存在也会跳过。两个后端之间没有可比较的保存版本或提交序号。

影响：用户看到保存成功，却读到旧世界，误以为新进度丢失。

修复方向：保存统一的提交 ID、版本与时间信息；两个后端都存在时选择最新有效提交，不能靠删除旧副本作为唯一正确性保证。

### A06 · P2：外层存档校验接受会破坏 UI 的值

位置：[归一化校验](../../lib/persist/local-save-normalize.ts#L231)、[事件恢复](../../app/mission-control/use-local-save.ts#L683)。

复现：`timeScale: -1`、`events: [null]` 的未启动存档被归一化接受。

负倍率会进入要求非负数的时间倍率组件；null 事件在恢复时读取 `entry.id` 会抛异常，而且之前已有状态被更新。这不是由 TypeScript 类型可以防住的输入。

限定：探针使用未封装的兼容存档；校验和完整的正常写入结果通常不会随机出现这些值。校验和验证的是内容是否变化，不等于结构合法。旧格式、手动导入或带正确校验和的错误内容仍需要语义校验。

修复方向：校验完整 LocalSave schema，包括布尔值、正倍率、非负时间、事件元素及字段；外层校验应在任何 UI 写入之前完成。

### A07 · P1：一次人工事故注入会重置 AI 的持续记忆

位置：[人工干预入口](../../app/mission-control/use-god-interventions.ts#L155)、[存档覆盖附加状态](../../app/mission-control.tsx#L1013)。

复现：提交正常的 `micrometeoroid` 因果事件，Worker 接受。收到回执前，UI 已调用五类 snapshot 的空状态构造器，清空航行志、观察哨、部门立场、乘客社会和收件箱，并重置乘客观测。

需要区分：乘客社会和收件箱可被之后的 Worker telemetry 再同步；不能声称五类数据都永久丢失。但航行志、观察哨、部门立场的 React 状态在这条回执路径没有同样恢复，并会参与后续决策与存档。

影响：本应观察“既有舰长如何应对突发事故”，却在事故发生时重置了其持续记忆。即使物理操作最终被拒绝，重置也已发生。这会削弱因果叙事和策略连贯性。

修复方向：事故应使在途观察失效、取消过期决策并触发新观察；只有新建世界或明确重置操作才清空长期记忆。

### A08 · P1：无效密钥遭遇 401 后，网关仍宣称 ready

位置：[服务器状态](../../lib/llm/index.ts#L1106)、[决策触发门槛](../../app/mission-control.tsx#L1851)、[失败后恢复日程](../../app/mission-control/captain-decision-coordinator.ts#L1491)。

复现：所有 secret 引用返回非空测试字符串，模拟 provider 返回 401；调用失败前后 `status().ready` 都为 true。没有真实网络请求。

原因：ready 主要代表“配置中引用的密钥非空且当前不在 retrying”，不代表端点可调用。401 的失败状态不被保留。UI 却把这个字段用于“端点已就绪”和能否发起关键决策。

关联风险：决策失败删除触发 key、恢复到期日程，并释放等待状态；后续遥测或状态刷新可以再次触发同一决策。底层虽有单次调用重试上限，整个决策周期没有对应的永久错误熔断。持续 401 的实际循环频率未在浏览器测量。

修复方向：分离 configured、reachable、authenticated、retrying、failed；鉴权及配置错误等待配置变更或人工重试，临时错误使用有上限的周期退避。状态 GET 失败还应将上次健康信息标为陈旧。

### A09 · P1：返航距离以原目的地为出发位置，尚未出发也被要求飞回 11.9 光年

位置：[任务修订处理器](../../lib/sim/command-handlers/operations.ts#L95)、[重设航程计数](../../lib/sim/index.ts#L1828)。

复现：太阳系出发的任务，仿真时间 0、累计跃迁 0；下达返回太阳系命令后，实际 Worker 接受，并生成 `11.89999474075514 ly` 的返航距离。

原因：return 分支把 `currentMission.destination` 当作当前位置；divert 分支又从 `originalOrigin` 计算。底层随后清零 completedDistance 和 jumpsCompleted。模型有原始起点与目标，但缺少与累计航行一致的改航起点。

影响：改航、返航不能正确表达“现在在哪、还需走多远”，使后续跳跃次数、耗能与风险决策建立在错误航程上。这是业务模型错误，不是星表坐标精度问题。

修复方向：保存实际航路节点或明确的当前航程坐标；把已完成历史与新航段分开。返航从当前位置计算，零距离应有明确到达或无需返航结果。

### A10 · P1：实际目的地已经改变，航程标题和星图仍显示旧目的地

位置：[航程视图](../../app/ui/views/voyage-view.tsx#L61)、[星图参数](../../app/ui/views/voyage-view.tsx#L347)、[命令回执](../../app/mission-control.tsx#L1271)。

复现：接续 A09 的真实 Worker 回执，用真实 VoyageView JSX 渲染。Worker 目的地为“太阳系”；渲染标题仍为“太阳系 → 鲸鱼座 τ”；StarMap 参数仍为 `tau-ceti`。

原因：React 的开局表单 destination 与 Worker journey.destination 是两套状态。命令回执更新了 engineState，但没有使活动航路展示读取它；页面却同时使用新航程的距离和进度，形成混合信息。

修复方向：区分“最初任务契约”和“当前执行航路”；当前航程视图、星图和剩余距离从同一活动任务投影获得，原指令单独保留并标注。

## 其他已定位的工程风险

**存档屏障不覆盖全部 UI 元数据提交时点。** `use-local-save.ts:479` 在等待在途事务之前捕获 metadata；`mission-control.tsx:1008` 之后只校正仿真时钟并用旧 metadata 覆盖附加状态。若排队命令在等待期间改变日程、部门立场或事件，物理快照和元数据可能属于不同提交。这里已定位时间顺序风险，但尚未执行完整 React 调度下的竞态复现，不能与 A01–A10 的确定性探针等同。

**Worker 异常缺少恢复状态机。** `mission-control.tsx:1340` 清理部分命令状态并暂停，却没有重建 Worker，也没有清空/拒绝全部 pending save、load、intervention。挂起的请求缺少明确期限。异常发生在存档期间可能使后续存档与读档持续被阻止。需要以 Worker 终止/消息丢失为故障注入场景验证。

**AI 健康查询被放在命令执行的关键路径上。** `captain-decision-coordinator.ts:1388` 已拿到模型结论后，仍先 await 一次状态 GET，随后才进入命令派发。这个读操作的网络异常会进入整轮决策失败分支，非关键观测依赖可以否决已有决策。应将健康展示更新与命令提交解耦，并为整轮设置可中止的期限。

**运行边界不一致。** Vite 配置包含 Sites/Cloudflare 运行支持，但 `/api/llm/*` 明确只接受 loopback hostname（`_server.ts:615`）。这是当前代码的限制：部署到普通站点域名会被拒绝，不能直接视为可用的在线版本。反过来，检查 URL hostname 也不验证 TCP 对端；若显式开放 LAN，不能把它当作完整客户端鉴权。默认生产启动绑定 127.0.0.1，因此不将其夸大成默认公网暴露漏洞。

**结束条件缺少统一产品表达。** 主界面和 final report 只沿 arrived 路径结束，实际模型还可 stranded，且人口可以死亡。现有代码没有同等完整的搁浅、失败报告与重新开始流程。这是产品状态设计缺口；“全员死亡是否必须终止模拟”仍需由产品规则确定，不能擅自替用户决定。

## 前端为何给人廉价、混乱的感觉

这里需要分开“审美偏好”和“工程问题”。没有截图实测，不评价具体屏幕是否溢出；但代码足以说明以下设计矛盾。

1. **展示气氛比阅读任务更受重视。** 开局界面同时强调 09 物理域、40 智能节点、2,120 个体与大量英文标签，故障配置却把 npm 命令和环境变量直接放在普通使用流程里。初次用户被要求理解内部架构，但端点是否真正可用仍无可靠反馈。
2. **字号体系没有落实。** `globals.css` 的 body 是 13px，多处常用数据标签为 8–10px，例如 `.end-metrics span` 8px、`.api-usage-item span` 8px；存在 7px 文本。文件后部虽然补了字号 token，旧选择器仍大量使用固定小字号。是否达成特定无障碍标准需要进一步实测，不能仅凭字号下合规结论。
3. **“当前状态”与“历史记录”混在一起。** 告警是历史去重集合，任务标题取旧表单，进度取新物理状态；用户看到很多信息却无法判断哪个是当前事实。先修语义一致性，再调整颜色、面板和动画。
4. **交互原语不完整。** 自制模态只加 ARIA 属性，快捷键跨控件生效；按钮没有清晰的 initializing、restoring、failed 状态。功能看似具备，连续操作和异常路径并没有完整设计。
5. **演出状态没有覆盖真实运行状态。** VoyageView 顶部只用 missionStarted 决定“航路执行中”；动画也只拿到 missionStarted。暂停、抵达、搁浅与 AI 故障没有统一的视图模型，局部文案可以互相矛盾。

视觉改造应围绕四个可直接回答的问题组织：船现在处于什么状态；最危险的未解决问题是什么；舰长正在做什么且依据是什么；用户当前有哪些有效操作。诊断细节进入可展开区域，日志保留事件因果和命令回执，减少常驻说明文字与装饰性指标。

## 架构与测试为什么没拦住问题

`mission-control.tsx` 约 93 KB，`worker.ts` 约 145 KB，决策协调器约 55 KB，`globals.css` 约 130 KB。体积本身不是缺陷，但这些文件同时承担多个可独立失败的职责。现有 hook 拆分仍通过大量可变 ref、setter 和回调互相连接，实际上把大组件分成了多份共享可变状态。

尤其是航行志、观察哨和部门立场既有 React 副本，也有 Worker snapshot sidecar，还会在存档和决策完成时相互覆盖。A02、A07、A10 都能追溯到“谁拥有状态、何时提交”没有统一答案。

测试有实质价值，但保障范围需要准确说明：

- `tests/rendered-html.test.mjs` 很多断言是对源码做正则匹配。它们能证明某段文字或标识符存在，不能证明焦点行为、暂停恢复或连续读档正确。
- 路由与 SSR 测试直接导入 dist；默认 `npm test` 不先构建。这次实测出现了“当前源码已经修复，旧产物仍报错”。同样机制也可能掩盖源码中尚未构建的回归。
- `long-voyage-conservation-smoke.test.mjs` 的完整 Worker 联动只推进 1 小时，之后把几个领域分别推进 1 天。输出确实为 `coupledSimSeconds: 3600`、`domainDaySeconds: 86400`。这不能证明整舰耦合连续一天、更不能证明完整星际远航可靠。
- lint 的 28 个错误不应算作 28 个已证实业务 bug，其中包含规则对可变 ref 参数的静态分析告警；但质量门禁当前确实不能通过，需要修正代码结构或逐项有依据地配置规则。

性能诊断也应分层：初始运行快照 JSON 约 2.62 MB，初始遥测 JSON 约 85 KB；本机 Node 的遥测 structuredClone 约 0.6ms。构建产物中 Three.js 约 724 KB、Worker 约 537 KB、主界面约 367 KB，都是未 gzip 大小。Three.js 已动态加载，不能称为所有内容都同步塞入首屏。以上是负载线索，不是浏览器帧率或真实网络传输测量。

需要补的高价值测试是：报警→确认→恢复→复发；失败读档保持原世界；运行→读回配置→再次启动；事故保留长期记忆；改航后的模型、视图、存档一致；备用写入后恢复旧后端；401 不再无限触发决策；Worker 崩溃使所有挂起操作可结束。它们比继续增加源码字符串断言更能保护产品。

## 建议修复次序

**第一步：恢复数据与操作可信度。** 先修 A01、A02、A03、A05、A07；把启动、运行、暂停、保存、恢复、故障变成显式状态迁移。保存和加载统一提交身份，失败不得留下半个新世界。

**第二步：统一活动任务模型。** 修 A09、A10，明确当前位置、既往跃迁、新航段和原始契约。AI、Worker、星图及存档使用同一活动航路事实。

**第三步：让外部服务故障可控。** 修 A08 和状态 GET 的关键路径依赖，建立持久的错误分类、重试上限、退避、取消及恢复入口。

**第四步：重做交互结构与阅读层级。** 先补完整按钮/弹窗/快捷键行为及准确状态，再调整字号、密度、主次布局、响应式和视觉风格。用真实浏览器覆盖桌面、小屏、200% 缩放、键盘操作、无 WebGL 及服务断开场景。

**第五步：修复验证链。** API/SSR 测试绑定当前构建；将源码形状检查与行为测试分开；恢复 lint 门禁；采用受控端点完成整段航程端到端测试，再用少量真实模型评估策略表现与调用成本。

不建议先推翻已有物理域，也不建议继续通过给大组件增加 ref 或条件分支来补洞。应优先替换跨层状态编排契约，使已存在的局部模型能够被可靠地使用。
